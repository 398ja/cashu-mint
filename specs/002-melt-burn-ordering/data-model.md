# Phase 1 Data Model: Melt Path Burn-First Ordering and Burn-Amount Check

**Feature**: 002-melt-burn-ordering
**Date**: 2026-05-22
**Source**: Phase 0 research (`research.md`)

Two new entities + two Flyway migrations + one cross-repo change
(cashu-vault `proof_entity` gets a nullable `melt_saga_id` column).
All amount fields are `long`. All timestamps come from PostgreSQL
`now()`. Hibernate Envers audit-tracks `MeltSaga.current_state`.

---

## Entity: MeltSaga

Durable record of a single NUT-05 melt attempt. Source of truth
for the saga state machine. Envers audit-tracked on
`current_state`, `payment_hash`, and `provider_event_id`.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `melt_saga_id` | `VARCHAR(64)` | PK, NOT NULL | UUID generated by the mint at saga creation |
| `quote_id` | `VARCHAR(64)` | NOT NULL, UNIQUE | The melt quote being executed; the unique constraint plus FR-005 enforces "at most one saga per quote in non-terminal state" — terminal sagas keep the row but the index will need to be a partial unique excluding terminal states; see Indexes |
| `invoice_amount` | `BIGINT` | NOT NULL, > 0 | The Lightning invoice amount (or equivalent) the saga is settling |
| `exact_fee_reserve` | `BIGINT` | NOT NULL, >= 0 | Computed by the mint per research R1 |
| `asserted_fee_reserve` | `BIGINT` | NULLABLE | What the caller asserted; for forensics & cross-check |
| `input_amount` | `BIGINT` | NOT NULL, > 0 | `sum(proofs.amount)` for the saga's input proofs |
| `proof_count` | `INTEGER` | NOT NULL, > 0 | Number of input proofs |
| `current_state` | `VARCHAR(32)` | NOT NULL, default `PROOFS_HELD` | See state machine below |
| `payment_hash` | `VARCHAR(255)` | NULLABLE | Set on `PAYMENT_SENT` if the provider returns it |
| `provider` | `VARCHAR(64)` | NOT NULL | Stable gateway identifier (matches spec 001 R6) |
| `provider_event_id` | `VARCHAR(255)` | NULLABLE | Filled when a provider response carries one |
| `payment_outcome_reason` | `TEXT` | NULLABLE | Free-text reason from `PaymentOutcome.DefinitiveFailure` / `Unknown` |
| `melt_response_cache` | `JSONB` | NULLABLE | NUT-19 cached response body for terminal sagas (research R7) |
| `change_outputs_hash` | `CHAR(64)` | NULLABLE | If NUT-08 change return was requested, the hash of the change blinded outputs |
| `change_signatures_json` | `JSONB` | NULLABLE | Issued change signatures, returned on COMPLETED (research R6) |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, default `now()` | DB clock |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL, default `now()` | |
| `version` | `BIGINT` | NOT NULL, default 0 | JPA `@Version` |

**Indexes**:
- PRIMARY KEY (`melt_saga_id`)
- UNIQUE on (`quote_id`) — see note above; if terminal sagas need
  to coexist with new non-terminal attempts for the same quote
  (which the spec does NOT permit per FR-005), this becomes a
  partial unique index `WHERE current_state NOT IN ('COMPLETED',
  'FAILED')`. v1: full unique (one saga per quote_id ever).
- INDEX on `current_state` (operator dashboards)
- INDEX on `created_at`
- INDEX on `provider_event_id` (forensics)

**State Machine**:

```text
            (validate + insert MeltSaga + UPDATE proof_entity
             SET state=PENDING, melt_saga_id=? — single TX)
                  │
                  ▼
            ┌─────────────┐
            │ PROOFS_HELD │
            └──────┬──────┘
                   │ LightningPaymentPort.pay(quoteId, timeout)
                   │
        ┌──────────┴─────────────┐
        │                        │
   PaymentOutcome           PaymentOutcome
   .Success                 .DefinitiveFailure
        │                        │
        ▼                        ▼
  ┌──────────────┐          ┌────────┐
  │ PAYMENT_SENT │          │ FAILED │ (terminal)
  └──────┬───────┘          └────────┘
         │                  (proofs UNSPENT + melt_saga_id=NULL)
         │ commit:
         │   UPDATE proof_entity
         │     SET state=SPENT, melt_saga_id=NULL
         │   UPDATE melt_saga SET current_state=COMPLETED
         │   (optionally compute change via NUT-08)
         │
   ┌─────┴────────────┐
   │ success          │ failure (DB hiccup, vault timeout)
   ▼                  ▼
 ┌──────────┐  ┌───────────────────────────┐
 │COMPLETED │  │ PAYMENT_SENT_BURN_FAILED  │
 └──────────┘  └───────────────────────────┘
  (terminal)    (terminal; proofs PENDING; operator alert)

   Ambiguity branch:
            ┌─────────────┐
            │ PROOFS_HELD │
            └──────┬──────┘
                   │ PaymentOutcome.Unknown
                   ▼
              ┌─────────────────┐
              │ PAYMENT_UNKNOWN │
              └────────┬────────┘
                       │ scheduled checkPaymentStatus poll
              ┌────────┴────────┐
              │                 │
        provider returns   provider returns
        definitive success  definitive failure
              │                 │
              ▼                 ▼
       ┌──────────┐        ┌────────┐
       │COMPLETED │        │ FAILED │
       └──────────┘        └────────┘
   (No transition until provider confirms one way or the other.
    TTL expiry → operator alert; no auto-resolution.)
```

Transitions are expressed as compare-and-set conditional UPDATE
(same idiom as spec 001):

```sql
UPDATE melt_saga
SET current_state = 'PAYMENT_SENT',
    payment_hash = ?,
    provider_event_id = ?,
    updated_at = now()
WHERE melt_saga_id = ?
  AND current_state = 'PROOFS_HELD';
```

## Entity: MeltSagaTransition

Append-only timeline of every saga state transition. Hand-rolled
table (in addition to Envers' `melt_saga_aud`) because the
admin-only saga query endpoint (FR-010) needs to return a clean
ordered timeline cheaply, including transitions that don't
change `current_state` (e.g. polling attempts in
`PAYMENT_UNKNOWN`).

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `melt_saga_id` | `VARCHAR(64)` | PK part, NOT NULL, FK → `melt_saga.melt_saga_id` | |
| `seq` | `INTEGER` | PK part, NOT NULL | Monotonically increasing per saga |
| `from_state` | `VARCHAR(32)` | NULLABLE | `NULL` for the initial transition |
| `to_state` | `VARCHAR(32)` | NOT NULL | Target state (may equal `from_state` for polling no-ops) |
| `reason` | `TEXT` | NULLABLE | Free-form context (e.g. "payment provider returned 504") |
| `actor` | `VARCHAR(64)` | NOT NULL | `system`, `operator:<id>`, `poll:<n>` |
| `at` | `TIMESTAMPTZ` | NOT NULL, default `now()` | DB clock |

**Indexes**:
- PRIMARY KEY (`melt_saga_id`, `seq`)
- INDEX on `at` (time-window operator queries)

**Append-only contract**: same as the `IssuanceRecord` /
`WebhookEvent` rule from spec 001. No UPDATEs/DELETEs from
application code.

## Cross-repo change: cashu-vault `proof_entity.melt_saga_id`

Per research R3, the proof's exclusive-hold property is intrinsic
to the proof row. Cross-repo migration in cashu-vault:

```sql
ALTER TABLE proof_entity
  ADD COLUMN melt_saga_id VARCHAR(64) NULL;

CREATE UNIQUE INDEX uq_proof_held_by_one_saga
  ON proof_entity (id)
  WHERE melt_saga_id IS NOT NULL;

CREATE INDEX ix_proof_melt_saga_id
  ON proof_entity (melt_saga_id);
```

This is **out of scope** for this branch but is a prerequisite.
Tracked in cashu-vault's spec backlog. The mint-side code in
`PaymentAdapterLightningPort` / `MeltTask` writes `melt_saga_id`
via the vault REST API when transitioning `UNSPENT → PENDING` and
clears it on `PENDING → SPENT` or `PENDING → UNSPENT`.

Two SQL files in
`cashu-mint-jpa/src/main/resources/db/migration/`:

1. `V20260523_001__create_melt_saga.sql`
2. `V20260523_002__create_melt_saga_transition.sql`

Ordering: `melt_saga` first (target of the FK from

Online-safe: pure DDL on new tables; no existing-table column
changes in the mint database. Brief table-creation locks only.

The cashu-vault migration runs in cashu-vault's own Flyway runner
on its own schedule.

## Invariants (summary)

For every `MeltSaga` row:

- The proof rows referenced by the saga have either
  `melt_saga_id = melt_saga.melt_saga_id` (while saga is
  non-terminal) or `melt_saga_id = NULL` (when terminal +
  COMPLETED or FAILED).
- For every terminal `COMPLETED` saga, all referenced proofs are
  in `SPENT` state.
- For every terminal `FAILED` saga, all referenced proofs are in
  `UNSPENT` state.
- For every `PAYMENT_SENT_BURN_FAILED` saga, all referenced
  proofs are in `PENDING` state with
  `melt_saga_id = melt_saga.melt_saga_id`.
- `PAYMENT_SENT` precedes `COMPLETED` (and possibly
  `PAYMENT_SENT_BURN_FAILED`) for every saga that successfully
  reached external payment — verified by SC-003 via a
  `MeltSagaTransition` timeline assertion.
- `current_state IN ('COMPLETED','FAILED','PAYMENT_SENT_BURN_FAILED')
  ⇒ melt_response_cache IS NOT NULL` (for the NUT-19 idempotent
  retry contract).
- `change_signatures_json IS NOT NULL ⇒ current_state = 'COMPLETED'`
  (NUT-08 change return only after success per FR-013).

## Out of Scope

- Archival policy for terminal sagas (append-only growth).
- Cross-mint coordination (today: one mint per instance).
- Redis-backed in-memory cache of saga state (the database is fast
  enough at current scale; revisit if the saga query endpoint
  becomes a hot path).
- Operator UI for resolving `PAYMENT_SENT_BURN_FAILED` /
  `PAYMENT_UNKNOWN` — the spec only requires the admin query
  endpoint; UI design is a separate effort.
