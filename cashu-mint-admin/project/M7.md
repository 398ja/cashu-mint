# M7 API Interface (CLI Phase)

## Overview
Establish the admin API surface and supporting tooling with the CLI as the primary consumer. Browser-specific optimizations and
clients will be added only after the terminal workflow is complete.

## Technical analysis alignment
- Use the REST surface cataloged in
  [REST delivery layer](../../docs/explanations/technical-analysis.md#rest-delivery-layer)
  as the baseline schema and error handling model for generated clients.
- Align SDK publishing plans with the M7 guidance captured in
  [implications for milestones](../../docs/explanations/technical-analysis.md#implications-for-milestones)
  so CLI tooling and APIs evolve together.

## Deliverables
- OpenAPI (and proto, if gRPC) specifications covering all admin capabilities with machine-readable examples and schema descript
ions prioritized for CLI consumption.
- REST controllers with consistent error handling, pagination, filtering, and optimistic concurrency controls backing CLI comman
ds.
- SDK generation pipeline producing client libraries for supported languages and auto-generated CLI bindings.
- API gateway or edge configuration enforcing authentication, authorization, and request throttling tuned for CLI traffic patter
s.
- Developer portal or documentation site detailing endpoints, usage patterns, and CLI integration guidance.
- Tooling to version, test, and publish CLI clients whenever the API contract changes.

## Tasks
1. Define API versioning strategy, deprecation policy, and compatibility guarantees with CLI stability in mind.
2. Build validation middleware, serialization/deserialization layers, and error response contracts consumed by CLI clients.
3. Implement request tracing, correlation IDs, and structured logging for observability across CLI-triggered flows.
4. Generate and publish API documentation (Swagger UI, ReDoc) highlighting CLI usage patterns and regenerate CLI clients on sche
ma changes.
5. Provide sample automation scripts and Postman collections demonstrating end-to-end workflows executed from terminal contexts.
6. Add integration tests covering critical paths, auth scenarios, and rate limiting enforcement driven by CLI test harnesses.
7. Document API lifecycle processes (breaking changes, release notes) tailored to CLI operators and integrators.

## Exit Criteria
- The CLI can rely on a stable, versioned API surface with published schemas and generated clients.
- Observability, security, and throttling policies protect CLI traffic in production.
- Documentation and automated tests cover expected automation and integration scenarios without referencing a web client.

## Deferred Web Scope (Post-CLI)
- gRPC/streaming optimizations and UI embedding guides created once web work begins.
- Additional developer portal sections tailored to browser integrations scheduled after CLI adoption milestones.
