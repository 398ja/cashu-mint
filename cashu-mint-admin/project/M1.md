# M1 Architecture Foundations and Domain Entities

## Objective
Establish the Clean Architecture scaffolding for the admin service so that subsequent milestones can plug features into a
consistent set of enterprise rules, use-case ports, and adapter boundaries.

## Scope
- Model the core aggregates and value objects described in the technical analysis: `MintAggregate`, `ConfigurationSet`,
  `OperatorAccount`, `AuditTrail`/`DomainEvent`, and `NotificationPolicy`.
- Define repository interfaces and persistence schemas that respect the separation between write models and read projections.
- Provide initial adapters that allow the CLI and REST layers to call stubbed use-case ports while the feature work is sequenced.

## Workstreams
### Enterprise Rules
- Implement immutable value objects for identifiers, lifecycle states, configuration revision IDs, and policy metadata.
- Encode invariants for lifecycle transitions, configuration compatibility, role delegation, and notification escalation.
- Capture audit metadata (who/what/when) inside entities to guarantee that later adapters only append context, never invent it.

### Application Business Rules
- Declare input/output ports for all six use cases: lifecycle, configuration, health monitoring, operational controls, access
  administration, and notifications.
- Provide base interactors that throw `UnsupportedOperationException` but already enforce cross-cutting validation (e.g.,
  non-empty IDs, version tags) so feature teams can focus on happy-path behaviour.

### Interface Adapters
- Create skeletal CLI commands and REST controllers that translate external payloads into the new port request models.
- Implement mapper utilities for JSON/YAML payloads and table/JSON rendering without business logic.
- Introduce persistence adapter contracts for repositories and transactional outbox handling.

### Frameworks & Drivers
- Provision Spring Boot modules, Picocli (or equivalent) bootstrap wiring, and database migrations for the foundational tables
  (mints, configuration revisions, operator accounts, audit events, notification policies).
- Set up local development profiles using PostgreSQL/H2 with repeatable Flyway or Liquibase migrations.
- Configure logging, tracing IDs, and error handling filters consistent with the layering expectations.

## Deliverables
- Domain module containing entity/value object implementations with unit tests covering invariants and error paths.
- Repository interfaces plus SQL migration files establishing normalized write models and initial read projection views.
- Skeleton CLI commands (`mint`, `mint config`, `mint users`, `mint alerts`) that exercise request/response DTO mapping.
- REST controller placeholders returning HTTP `501 Not Implemented` yet wired through authentication filters and serializers.
- Documentation outlining architectural decisions, directory layout, and developer onboarding instructions.

## Acceptance Criteria
- Entities compile without framework dependencies and enforce the state transitions documented in the technical analysis.
- Repository interfaces persist and retrieve aggregates against the real database in integration tests (H2/PostgreSQL).
- CLI and REST layers successfully invoke the stub interactors, proving wiring and validation without final behaviour.
- Build pipeline executes unit tests, integration smoke tests, and static analysis for the newly added modules.
